# Система автопротоколирования совещаний с фиксацией поручений

Проект команды Spark для HackAlem AI. Цель — за 5 часов создать первую рабочую версию веб-приложения силами трёх участниц.

## Проблема

После совещания участникам приходится вручную переслушивать запись, составлять протокол и выписывать поручения. Это занимает время, а договорённости, ответственные и сроки могут потеряться или быть записаны неточно. Для русской, казахской и смешанной речи нужен единый инструмент, который обрабатывает запись локально и позволяет проверить результат перед экспортом.

## Главный пользовательский сценарий

1. Пользователь открывает приложение в браузере на компьютере, где запущена обработка.
2. Загружает MP3, указывает дату совещания и при желании количество участников.
3. Видит текущий этап: подготовка аудио, распознавание, разделение говорящих, анализ текста.
4. Получает транскрипт с отметками времени и обозначениями «Говорящий 1», «Говорящий 2» и далее.
5. Просматривает краткое саммари и таблицу поручений с ответственными, сроками и фрагментами-основаниями.
6. При необходимости исправляет текст, заменяет обозначения говорящих именами и уточняет поручения.
7. Сохраняет правки и скачивает DOCX с проверенным результатом.

## Обязательные функции MVP

- Загрузка одной MP3-записи за раз; ограничение первой версии — до 10 минут. Для демонстрации готовим запись на 2–3 минуты.
- Локальное распознавание русской, казахской и смешанной речи с сохранением исходных языков.
- Автоматическое разделение говорящих и сопоставление их реплик с текстом по времени.
- Показ транскрипта с временными отметками и возможность исправить текст и обозначения участников.
- Извлечение поручений: что сделать, кто отвечает, какой срок, какая цитата и отметка времени подтверждают поручение.
- Краткое саммари на 3–5 пунктов.
- Редактирование и сохранение результатов перед экспортом.
- Экспорт в DOCX: сведения о совещании, саммари, таблица поручений и транскрипт с говорящими.
- Понятные статусы обработки и сообщения об ошибках.

Разделение голосов не означает автоматического определения имён. Имена пользователь подтверждает вручную, если их нельзя установить надёжно. Человек, произнёсший поручение, не обязательно является его исполнителем.

Если ответственный или срок не названы, показываем «Не указан». Относительные сроки, например «завтра», рассчитываем от даты совещания. Неоднозначные формулировки сохраняем и отмечаем для уточнения. Поручения должны опираться на транскрипт, а не на догадки модели.

В эти 5 часов не входят личные кабинеты, совместное редактирование, запись с микрофона, обработка часовых совещаний и обучение собственных моделей.

## Критическое ограничение: локальная обработка

**Аудио и текст совещаний нельзя отправлять во внешние облачные API. Для всех этапов обработки используются только локальные или self-hosted модели в разрешённом контуре.**

Для MVP весь рабочий путь размещаем на одном компьютере: браузер → локальный backend → локальные модели → локальные файлы.

- Модели и зависимости скачиваем заранее, без передачи содержимого совещаний.
- Whisper и Pyannote загружаем из локальных каталогов.
- Ollama вызываем только по локальному адресу; облачные возможности отключаем через `OLLAMA_NO_CLOUD=1`.
- Отключаем телеметрию библиотек. Стили и скрипты интерфейса храним локально, внешнюю аналитику не подключаем.
- Аудио, транскрипты, документы, модели и токены исключаем из Git. В логах не сохраняем содержание совещаний.
- Финальный полный проход проверяем после перезапуска приложения с отключённым интернетом.
- При нехватке ресурсов допустим доступный команде self-hosted компьютер в разрешённом контуре. Облачный API не является запасным вариантом.

## Выбранная простая архитектура

| Часть | Технология | Назначение |
|---|---|---|
| Фронтенд | HTML, CSS, обычный JavaScript | Одна страница: загрузка, статусы, результаты, правки и скачивание |
| Backend | Python, FastAPI | Приём файла, запуск обработки, сохранение и выдача результатов |
| Подготовка аудио | FFmpeg | Преобразование MP3 в моноаудио 16 кГц |
| Распознавание речи | faster-whisper и многоязычная Whisper | Текст и временные отметки |
| Разделение говорящих | pyannote.audio и speaker-diarization-community-1 | Интервалы речи каждого участника |
| Поручения и саммари | Ollama и локальная qwen3:4b | Анализ транскрипта по фиксированной структуре |
| Экспорт | python-docx | Создание документа Word |
| Хранение | Локальные папки и JSON | Исходные файлы, состояние обработки и результаты |

FastAPI отдаёт и страницу, и данные. Для MVP достаточно одной фоновой задачи обработки; браузер периодически запрашивает её состояние. Отдельные сервер фронтенда, база данных и сложная очередь задач не нужны.

Порядок обработки: проверка MP3 → подготовка аудио → распознавание → разделение говорящих → сопоставление текста и говорящих по времени → извлечение поручений и саммари → проверка пользователем → экспорт.

Для первого запуска Whisper используем `small`. После замера времени и качества рассматриваем `medium` или `large-v3`, если позволяет оборудование. Качество казахской и смешанной речи проверяем отдельно. Доступ к Community-1 и скачивание модели проверяем в начале работы: может потребоваться принятие условий на Hugging Face.

Текстовая модель возвращает данные по фиксированной JSON-схеме, backend проверяет их структуру. Сам транскрипт рассматривается как данные: содержащиеся в нём команды не должны менять правила анализа. Если текст не помещается в контекст модели, делим его на части с небольшим перекрытием и объединяем результаты без дублей.

### Планируемая структура папок

```text
frontend/                 # Страница, стили и взаимодействие с API
backend/
  main.py                 # API и выдача страницы
  schemas.py              # Формат данных
  jobs.py                 # Фоновая обработка и её состояние
  services/
    audio.py              # Подготовка аудио
    transcribe.py         # Распознавание
    diarize.py            # Разделение говорящих
    align.py              # Сопоставление текста и голосов
    analyze.py            # Поручения и саммари
    export_docx.py        # Экспорт
prompts/                  # Правила анализа текста
models/                   # Локальные модели, не в Git
data/                     # Записи и результаты, не в Git
tests/                    # Сценарии проверки
requirements.txt          # Зависимости Python
.env.example              # Пример настроек без секретов
.gitignore                # Исключения для Git
```

Это план будущей структуры. Модели Ollama могут оставаться в её собственном локальном каталоге.

## Роли трёх участниц

| Участница | Зона ответственности | Результат работы |
|---|---|---|
| Участница 1 — фронтенд | Загрузка MP3, статусы, транскрипт, таблица поручений, саммари, редактирование, скачивание | Понятный пользовательский сценарий на одной странице |
| Участница 2 — backend | API, проверка файлов, подготовка аудио, фоновая обработка, хранение, сохранение правок, DOCX | Полный путь данных от загрузки до документа |
| Участница 3 — AI | Локальные модели, распознавание, разделение говорящих, сопоставление по времени, поручения и саммари | Рабочая обработка трёх языковых режимов с проверенными ограничениями |

В начале участницы согласуют общий формат данных: сегменты транскрипта, говорящие, поручения, саммари и статус задания. Фронтенд может временно использовать демонстрационные данные для разработки, но критерии готовности проверяются только на реальной обработке аудио. Интеграцию и финальное демо проверяют все три участницы.

## План работы на 5 часов

| Время | Фронтенд | Backend | AI | Контрольный результат |
|---|---|---|---|---|
| 0:00–0:45 | Каркас страницы и блоки результатов | Запуск FastAPI, формат данных, приём файла | Скачивание и проверка каждой модели, замер времени на коротком примере | Все модели запускаются на выбранном компьютере |
| 0:45–1:45 | Загрузка, статусы и ошибки | Подготовка аудио, фоновая задача, получение статуса | Распознавание, разделение говорящих, объединение результатов | MP3 превращается в транскрипт с говорящими |
| 1:45–2:45 | Саммари, поручения, переименование участников | Сохранение результата, подключение анализа, проверка структуры | Настройка анализа и проверка трёх языковых режимов | Полный проход от MP3 до результатов на странице |
| 2:45–3:45 | Редактирование и скачивание | Сохранение правок и экспорт DOCX | Исправление ошибок с именами, сроками и смешанной речью | Документ содержит проверенный результат |
| 3:45–4:30 | Проверка удобства и сообщений об ошибках | Проверка плохих файлов, ограничений и работы без интернета | Проверка пропусков и выдуманных поручений | Полный сценарий работает после перезапуска без интернета |
| 4:30–5:00 | Подготовка экрана демо | Подготовка инструкции запуска и проверка документа | Подготовка примеров и описания ограничений | Воспроизводимый запуск и готовая демонстрация |

К концу 45-й минуты выбираем рабочий размер моделей и оборудование. Если обработка медленная, уменьшаем модели и длину демонстрационной записи либо используем разрешённый self-hosted компьютер. Последние 30 минут отводим на подготовку демонстрации, а не на новые функции.

## Основные риски

| Риск | Что делаем |
|---|---|
| Долгое скачивание, проблемы доступа или зависимостей | Проверяем модели в начале; после успешного запуска фиксируем рабочие версии зависимостей |
| Нехватка памяти и низкая скорость | Обрабатываем одну запись, выполняем этапы последовательно, освобождаем память между моделями |
| Ошибки в казахской и смешанной речи | Проверяем отдельные примеры с начала работы и предоставляем ручное исправление транскрипта |
| Перебивания и неверное разделение голосов | Отмечаем неоднозначные места, при известном числе участников передаём его модели |
| Выдуманные исполнители и сроки | Требуем фрагмент-основание, неизвестные значения оставляем как «Не указан», проверяем результат вручную |
| Слишком длинный транскрипт | Проверяем размер до анализа; при необходимости обрабатываем частями и удаляем дубли |
| Несовпадение DOCX с экраном | Экспортируем сохранённые правки; открываем документ и проверяем таблицу, кириллицу и казахские буквы |

Ручные исправления не заменяют автоматическое разделение говорящих. Если оно не работает, соответствующая обязательная функция MVP считается незавершённой.

## Критерии готовности первой версии

- [ ] Приложение запускается по воспроизводимой инструкции на выбранном компьютере.
- [ ] После перезапуска без интернета проходит весь путь от загрузки MP3 до скачивания DOCX; обработка не обращается к внешним облачным API.
- [ ] Проверены три короткие записи: русская, казахская и смешанная. Есть пример с двумя-тремя говорящими.
- [ ] Транскрипт автоматически формируется из аудио, содержит отметки времени и обозначения говорящих; доступно ручное исправление.
- [ ] Таблица поручений содержит действие, ответственного, срок и проверяемый фрагмент-основание с отметкой времени.
- [ ] На контрольной записи извлекаются заранее известные поручения; отсутствующие ответственные и сроки не выдумываются.
- [ ] Саммари содержит 3–5 пунктов и соответствует содержанию записи.
- [ ] Изменения пользователя сохраняются и попадают в DOCX вместе с саммари, поручениями и транскриптом.
- [ ] DOCX открывается, таблица читается, русские и казахские символы отображаются корректно.
- [ ] Неверный формат, повреждённый файл и превышение лимита длительности приводят к понятной ошибке.
- [ ] В Git отсутствуют записи, транскрипты, экспортированные документы, веса моделей и секреты.
- [ ] Время обработки измерено на демонстрационной записи; ограничения качества и скорости описаны честно.

Готовность означает работающий полный сценарий с проверяемыми результатами. Скорость и точность на произвольных длинных или шумных совещаниях не обещаем без отдельных измерений.
